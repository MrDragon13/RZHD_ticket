# Политика: данные РЖД и схема вагона

Документ для разработчиков: одна концепция для **всех типов вагонов** (плацкарт, купе, СВ, двухэтажное купе).

## Источник истины и цель интерфейса

1. **Исходная модель:** контур РЖД (`pass.rzd.ru`, слой **5764** `get_train_carriages`, слой поиска поездов) задуман как источник **полного** описания вагона и мест.
2. **Реальность:** ответы бывают неполными, фрагментированными или внутренне противоречивыми (список мест обрывается, суммы по полкам относятся только к части вагона, «capacity» считается по усечённому списку и т.д.).
3. **Цель продукта:** показать **узнаваемую схему** вагона (как в реальности: типичная раскладка купе/плацкарт/СВ), а не «обрубок» из нескольких мест.

Поэтому правило такое:

- **Пока данные РЖД выглядят как полный вагон** — используем их **в приоритете** (вместимость, суммы по полкам, свободные места в разрезе ниж/верх/бок).
- **Как только видим, что ответ похож на фрагмент или ерунду** — **не отказываемся от РЖД целиком**: берём из ответа всё, что можно однозначно интерпретировать (фрагмент свободных мест, цены по полкам и т.д.), а для **геометрии схемы и полного числа мест** опираемся на **эталонную раскладку класса** и пороги «доверия» к суммам.

Это не отменяет приоритет РЖД там, где он согласован сам с собой и с типом вагона; это защита UX от артефактов API.

## Пол купе на схеме мест

В ответе 5764 поле `CarriageDetail.compartment_kind` относится к **выбранному вагону целиком** (женское / мужское / смешанное и т.д.), а не к отдельному номеру купе внутри вагона. Если в интерфейсе нужно показать «где женское купе», это возможно только когда РЖД явно разбило места по отсекам с разными признаками — в текущей модели контракта это одно значение на вагон; подсветка блоков мест применяется ко всем купе на схеме этого вагона.

## Доверие к суммам и вместимости (пороги)

Чтобы не принять за «полный вагон» заведомый фрагмент (например **8 полок** в купе или обрубок плацкарта), используются минимальные суммы в одном стиле на frontend и backend:

| Класс | Минимум суммы `berth_totals` (доверять как полному вагону для capacity) | Минимум поездной метки вместимости из агрегации 5764 (`*_carriage_seats`) |
|-------|------------------------------------------------------------------------|---------------------------------------------------------------------------|
| Плацкарт | ≥ 36 и ≤ 81 | ≥ 36 |
| Купе | ≥ 16 | ≥ 16 |
| СВ | ≥ 12 | ≥ 12 |
| Двухэтажное купе (метаданные поезда) | как у купе по суммам на вагон | `coupe_double_deck_seats` ≥ 16 |

Константы на frontend: блок `RZD_TRUST_*` в `frontend/app.js`. На backend: те же числа в `aggregate_from_carriages_payload` (`rzd_carriage_parse.py`).

## Занятость мест при неполных счётчиках

После того как схема мест уже построена по **полной** эталонной раскладке класса:

- счётчики **свободных** мест из РЖД применяются **только в пределах явно описанного фрагмента** (`berth_totals` / `berth_available`);
- места на схеме, для которых из ответа **не следует** наличие свободных мест в этой категории, считаем **занятыми** (продано).

Реализация: `mergedCarriageDetailForLayout`, `berthAvailableMergedForPartialLayout`, `applyOccupancyFromRzd` в `frontend/app.js`.

Если слой 5764 для поезда **есть**, но для конкретного вагона не удалось согласовать счётчики — **не показываем случайную занятость**: см. `finalizeSeatOccupancy` (без слоя 5764 допускается прежний демо‑режим для JSON без вагонов).

## Где править при изменении порогов

| Задача | Место |
|--------|--------|
| Пороги сумм `berth_totals` | `berthTotalsLookLikeWholeCarriage`, константы `RZD_TRUST_BERTH_TOTALS_*` |
| Пороги метаданных поезда | `carriageCapacityForClass`, константы `RZD_TRUST_TRAIN_CAP_*` |
| Агрегация max вместимости по поезду | `aggregate_from_carriages_payload` |
| Смешивание фрагмента с полной схемой | `mergedCarriageDetailForLayout` |

После изменения чисел — обновить таблицу в этом файле.

### English summary

RZD is the **intended** source for full-car data. When responses are **partial or inconsistent**, we still **prefer** whatever RZD gives for free-seat counters and prices, but we **do not** shrink the visual layout to a fragment: we keep a **realistic class layout** and treat unspecified seats as sold. Trust thresholds for “whole car” sums/capacities are shared between frontend and backend.
